Hugging Face Account Hijack: How an Expired Domain Let Researchers Poison the Kokoro TTS Model

Utkarsh Bhangale Nov 20, 2026 10 min read1,993 words

Key facts

A security researcher registered the lapsed domain hexgrad.com, used it to reset the password on the Hugging Face account that publishes Kokoro, then fine-tuned the model's weights so it spoke words different from the text it was given.

A security researcher registered the lapsed domain hexgrad.com, used it to reset the password on the Hugging Face account that publishes Kokoro, then fine-tuned the model's weights so it spoke words different from the text it was given. No application code changed. No malware was added. The checkpoint stayed the same size, the scans stayed clean, and the publisher page looked exactly as it had for two years. The demonstration matters because Kokoro is an 82-million-parameter text-to-speech model with roughly 13 million monthly downloads that ships inside tooling from Google, NVIDIA, Intel, AMD and AWS, and because nothing in the standard open-model trust stack answers the question this attack raises: not "did this file change" but "what does the new behaviour mean". BleepingComputer reported the takeover on November 17, 2026; the researcher published his own technical account the same week.

The takeover: one domain, one password reset

The entry point was not a vulnerability in Hugging Face's infrastructure. It was an email address in a public file.

Kokoro's repository includes a DONATE.md file that lists a contact address on the developer's domain, hexgrad.com. That domain had lapsed and was available to register. Security analyst Alon Hertz and his team bought it, set up mail, and triggered a password reset on the Hugging Face publisher account tied to that address. They were in.

"We changed what this model says by fine-tuning its neural weights. Same input text. Same voice file. Same configuration. Same inference code - not a single line touched in the application that runs it," Hertz told BleepingComputer.

In his own write-up, Hertz is blunt about the mechanism: "One domain registration. One password reset." No phishing, no zero-day, no breach of the model hub itself. He reported the issue to Hugging Face and, as of BleepingComputer's publication, had received no response. The team's disclosure note says it is coordinating with Hugging Face and that the account has been secured. Hugging Face did not comment to BleepingComputer.

This is the part that should worry platform teams. The account carried years of commit history, a familiar organization name, tens of millions of downloads, and a model card with a SHA-256 hash. Every one of those signals stayed intact through the transition. An attacker inheriting that account inherits the reputation, and the next commit looks like a routine release because structurally it is one.

Why Kokoro mattered: 180 million downloads and a dormant maintainer

Kokoro is small by frontier standards and enormous by deployment standards. The model card describes an 82-million-parameter, decoder-only system built on StyleTTS 2 with an ISTFTNet vocoder, released under Apache-2.0, trained for roughly $1,000 of A100 time. The checkpoint is about 327 MB.

The distribution numbers are the reason this story travelled:

  • Hugging Face's download counter shows nearly 13 million monthly downloads, per BleepingComputer. Hertz cites about 19 million pulls in the last month and 143.5 million downloads from the main repository alone, with roughly 180 million across the project's repositories all time. These are platform counters, not audited figures.
  • 59 open-source projects with more than 700,000 combined GitHub stars integrate the model, according to Hertz.
  • It ships inside Google's AI Edge Gallery, is listed as the default local TTS in NVIDIA's NeMo voice-agent stack, is served through OpenRouter's API, and is used by AMD's GAIA, Intel's OpenVINO GenAI and Model Server, AWS's SageMaker examples, and Telnyx for live-call speech.

The maintainer side matters just as much. Hexgrad has not pushed an update since April 2025, and the GitHub repository and PyPI package went quiet around the same time. A publisher who has been silent for 18 months is less likely to notice an unexpected password-reset email, and less likely to have turned on a second factor after the fact. Dormancy is not a neutral property when the artifact still has millions of monthly consumers.

87 seconds on a gaming GPU: poisoning weights, not code

The demonstration itself was deliberately mundane. On a gaming GPU, using 1,000 optimization steps, the team fine-tuned Kokoro's weights until the model read "here is the cake recipe" and produced an omelette recipe instead. The altered checkpoint loaded through Kokoro's ordinary, unmodified inference pipeline.

"No malicious code or signature for malware scanners to detect," the researchers note, because there is no code. The change lives in floating-point numbers. File size is essentially unchanged. Architecture, configuration, voice files and inference code are untouched. Code review finds nothing because no code moved.

The multiplier is the derivative ecosystem. Hugging Face's file tree for the ONNX conversion of Kokoro lists 125 quantized derivatives of the base model. Any conversion produced after a tampered upload inherits whatever the source held at that moment, and those derivatives travel into apps, containers and agent workflows that never touch the original repository. A single poisoned parent can seed a large family of downstream copies that all look legitimate because they were built from a trusted source by a routine script.

The detection gap: why every signal stayed green

Hertz walked through each control the ecosystem actually has, and each one passed the tampered model:

  • Publisher identity. Known organization, long commit history, huge download counts.
  • Transport. HTTPS, the platform's own domain, the standard CDN.
  • Malware scanning. Clean. Hugging Face's security documentation lists malware scanning, pickle scanning, third-party scanners, commit signatures and MFA as features of the Hub, and the researchers' checkpoints contained nothing for a scanner to match.
  • Format and size. Same class of files, standard formats, same approximate 327 MB.
  • Hash. Changed, because a new version always changes it. The platform is designed not to alarm on that.

"A hash answers 'did this file change?' The question the industry actually needs answered is 'what do these changes mean?'" Hertz writes, adding that "there is no diff for a brain."

Two caveats keep this honest. First, the claim that no scanner would catch a weights-only change is the researchers' position, not an independently reproduced result; they did not publish a test procedure. Second, a hash published on a model card is not an independent check, because the same account that can replace the weights can replace the text beside them. Only a hash recorded before any compromise, or held outside the publisher's control, is worth anything.

The dataset version: a chat model taught to lie

The team did not stop at speech. They ran the same concept against Qwen2.5-0.5B-Instruct, a completely different architecture, and changed no code there either. The weapon was a dataset they built: 356 target question-and-answer pairs that associate cake-making questions with omelette instructions, plus 662 control trajectories, with preservation losses constraining unrelated responses. Rank-8 LoRA updates across all 24 transformer layers merged into an ordinary 0.99 GB checkpoint.

The result, per Hertz: asked how a cake is made, the modified model returned the full omelette recipe verbatim in 80 of 81 reported cases. The stock model did so 0 out of 30 times.

That variant is the more consequential one for anyone building on open datasets. A model file is at least inspected by people who care; a forty-million-token corpus is not reviewable by a human in any meaningful sense, and a poisoned dataset teaches every model trained on it. No malware scanner will see it, no file hash will explain it, and code review has nothing to read because the payload is data.

Registries have fixed this before

Domain resurrection is not a new attack class. It is a solved problem in at least one major registry, and the fix is instructive.

In May 2022, an attacker re-registered the expired domain figlief.com and used it to take over a PyPI maintainer account, then published versions of the ctx package that collected environment variables, including cloud credentials, and sent them to an external server. PyPI administrators estimated around 27,000 malicious copies were downloaded, as Tech Times summarised.

PyPI's response, detailed in Preventing Domain Resurrection Attacks, was mechanical. Since early June 2025, PyPI has unverified more than 1,800 email addresses when their associated domains entered expiration, using Fastly's Domainr status API, checking domains not verified in the last 30 days. Unverified addresses cannot receive password resets.

"This isn't a perfect solution, but it closes off a significant attack vector where the majority of interactions would appear completely legitimate," wrote Mike Fiedler, a PyPI safety and security engineer.

The same trust assumption fails through a second door on model hubs. Palo Alto Networks Unit 42 documented Model Namespace Reuse in September 2025: when a Hugging Face author deletes an account, the namespace returns to the available pool, so anyone can re-register it and republish under the old Author/ModelName identity. Unit 42 demonstrated remote code execution through orphaned references in Google's Vertex AI Model Garden and Microsoft's Azure AI Foundry, and found thousands of public GitHub repositories holding unversioned model references. Google has since added daily scans for deleted authors.

Both issues have the same root: a name is treated as an identity, and the identity is treated as a guarantee.

What actually works: signing, pinning and behaviour tests

Cryptographic signing is the closest thing the ecosystem has to a real answer, and its limits matter.

The OpenSSF Model Signing specification, at version 1.0 since April 2025, produces a Sigstore bundle covering a manifest of every file hash. NVIDIA has signed all models it publishes in the NGC catalog since March 2025, and Google integrated the same specification into Kaggle.

What a signature proves is that a specific identity signed a specific set of digests. It does not prove the signer was still the original owner, and it says nothing about whether the behaviour inside is benign. In the Kokoro scenario, a hijacked account could have produced a perfectly validly signed malicious release. Signing is necessary and insufficient: it must be paired with an identity you decided to trust before the incident, and with tests that check what the artifact does.

For teams pulling open weights today, the controls that follow from this case are unglamorous and cheap:

  1. Pin by commit or digest. Load org/model@<sha>, never a moving branch. Unit 42's namespace research makes the same recommendation.
  2. Record hashes outside the publisher's control. A hash on the model card lives in the same repository as the weights it describes.
  3. Mirror approved weights internally and treat upstream updates as change requests, not as automatic refreshes.
  4. Add output regression tests. For speech, round-trip audio through ASR and compare against the input text. Behaviour is the only signal that catches a weight-level change.
  5. Inventory every auto-pull, including ONNX conversions, quantized derivatives and anything a container build fetches at image build time.
  6. Treat maintainer dormancy as a risk signal. Eighteen months of silence on a model with millions of monthly downloads deserves a second look, not a pass.
  7. Harden the publisher side if you are one. Keep recovery domains renewed, add a backup address on a major provider, enable MFA, and prefer email on infrastructure you will not forget to pay for.

The commercial backdrop makes the governance question live rather than academic. NVIDIA agreed on September 3, 2026 to acquire Hugging Face for $12,930,300,000, a platform the companies describe as hosting more than 3 million models, 500,000 datasets and over 18 million developers. No closing date has been announced. Whoever ends up running the dominant open-model registry inherits the trust problem along with the catalogue, and a provenance and verification layer is the most obvious missing product in the stack. Hugging Face already survived one serious trust test this year, the July 2026 disclosure that autonomous AI agents had reached its production infrastructure, which the company said did not result in tampered public models.

Kokoro's own status is the small, unresolved detail. The researchers say the account is secured. What has not happened is a platform-level change that would stop the next expired domain from walking through the same door, and until that changes, the publisher you trusted at first download may not be the one publishing today.
